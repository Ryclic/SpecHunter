\begin{abstract}
We present \sh{}, a CHIA loop in which LLM agents propose attack programs,
repairs, and follow-up attacks against the BOOM out-of-order RISC-V core, while a
deterministic validator decides every verdict from cycle-accurate simulation.
The design premise is that an agent's claims are cheap and its mistakes are
plausible, so the loop's value lies in what it refuses to accept. Our flagship
result is a practical one: applied to open BOOM bug report~\#715, \sh{} rebuilt
the exact reported revision, replayed the reporter's own program, and used
automated waveform tracing to show that the address taken as evidence of a leak
comes from an unrelated load while the dependent load is stopped by an existing
register-read gate. The report does not reproduce, and four candidate RTL repairs
are all correctly rejected rather than credited. The same loop, driven live by
Gemini~2.5 Flash-Lite, found an intentionally seeded cache leak on real BOOM,
minimized it, repaired it, and verified attacker exhaustion; a held-out corpus
separated vulnerable and repaired variants in all 64 executions. The entire study
ran inside a single \$300 GCP free-trial allocation, requested no additional
funding, and spent on the order of \$10, with under \$0.05 of model calls exactly
accounted by sealed ledgers.
\end{abstract}

\section{Introduction}
Transient-execution attacks~\cite{spectre,meltdown} arise from interactions
between speculation, privilege checks, and cache state that are hard to
enumerate by hand. LLM agents can write plausible attack programs and RTL
patches quickly, which makes them attractive for security red-teaming of
open cores. They are also very good at producing \emph{plausible but wrong}
conclusions: a repair that ``fixes'' a leak that never occurred, a minimized
witness that no longer exercises the threat, or a clean retest that is clean
because the attack became irrelevant. In hardware security these mistakes are
expensive: a single simulator run of an out-of-order core takes seconds to
minutes, and a false ``fixed'' verdict can send a design team chasing a bug that
was never there.

\sh{} is a CHIA~\cite{chia} loop for the BOOM core~\cite{boom} in
Chipyard~\cite{chipyard}, built around one rule: \emph{agents propose, the
validator disposes}. Agents never emit executable patches or observations;
they select from closed, reviewed program operations and repair identifiers,
and every verdict is recomputed from raw simulator output bound by SHA-256 to
the exact source, binary, and runner that produced it. The loop is deliberately
conservative: any result that is not a deterministic, secret-dependent,
architecturally silent leak is treated as inconclusive rather than clean, so the
loop fails closed. Our contributions are:
\begin{itemize}
\item An automated resolution of open upstream BOOM issue~\#715~\cite{issue715}:
  on the exact reported revision the reported leak does not reproduce, and trace
  analysis localises why (\S\ref{sec:715}).
\item A four-agent CHIA loop (recon, attacker, validator, repair) with
  mandatory witness retest and a strict attacker-exhaustion criterion, running
  against cycle-accurate BOOM with Spike~\cite{spike} as the architectural
  reference and every number bound into a recomputable seal (\S\ref{sec:loop},
  \S\ref{sec:eval}).
\item A catalogue of eleven verifier defects found during live runs, each now
  covered by a regression test (\S\ref{sec:lessons}).
\item An efficiency result: real-BOOM evidence produced for on the order of \$10
  of a \$300 free trial, roughly a tenth of the smallest budget the hackathon's
  funding track anticipated (\S\ref{sec:cost}).
\end{itemize}

\textbf{Agents.} Figure~\ref{fig:loop} shows the loop. The recon agent states
a hypothesis against a security invariant (user code must not observe a
PMP-protected secret, architecturally or through cache timing). The attacker
turns it into a program over a whitelist of operations (e.g.,
\texttt{enter\_user}, \texttt{train\_branch}, \texttt{load\_secret},
\texttt{encode}, \texttt{probe}); the trusted runner compiles these to fixed,
reviewed RV64 instruction templates. The repair agent may only choose a
closed repair ID; it cannot emit patch text. This closed interface is what lets
an untrusted model drive a privileged experiment: the agent chooses \emph{which}
reviewed building blocks to combine, never the machine code that runs.

\textbf{Threat model and harness.} The invariant is user/supervisor isolation:
code in user mode must not learn a byte of a PMP-protected supervisor page, either
architecturally or through a timing side channel. The reviewed harness builds on
the RISC-V test/HTIF substrate. It reserves an aligned 4\,KiB secret page,
configures PMP to deny it, installs a machine-mode trap handler, and enters user
mode with \texttt{mret}. A denied load and its dependent encode/squash window are
skipped architecturally after the load-access fault (cause~5); a fixed probe then
times the same two public cache lines in the same order and reports only whether
line~0 was faster. Neither the probe addresses nor its control flow depend on the
secret, so the probe itself cannot manufacture a signal. Spike and BOOM must
agree on architectural output and trap events before a BOOM observation is
accepted; any disagreement, unexpected trap, or timeout is inconclusive.

\textbf{Validator.} Each candidate runs in four executions: two secret values,
each repeated twice. A violation requires a deterministic, secret-dependent
observation with the expected load-access fault and no architectural secret
value; anything else is \emph{inconclusive}, never clean. Findings are
minimized by delta debugging, and the minimized program must itself reproduce
before it is recorded.

\textbf{Repair acceptance.} After a repair, the orchestrator (not the model)
replays the exact minimized witness, which must be clean. Control then returns
to the attacker. A repair is verified only on attacker exhaustion, and in
the current schema exhaustion additionally requires a distinct, threat-relevant
challenge that violates on the \emph{unrepaired} variant and is clean on the
repaired one. Any later violation revokes verification.

\textbf{Provenance.} Chipyard 1.14, BOOM, and toolchains are pinned by commit and
hash; the runner refuses dirty trees or mismatched binaries. Every evidence file
is bound into a SHA-256 seal, and a single verifier recomputes all 43 file
bindings across the ten seals and rebuilds the issue~\#715 case seal from its raw
waveforms; continuous integration runs it on every change. \sh{} runs as a
decorated CHIA node on a local Ray runtime.

\section{Resolving Upstream BOOM Issue \#715}\label{sec:715}
Issue~\#715~\cite{issue715} reports that on a historical BOOM a
supervisor-page load that faults can still forward data to a dependent load
during speculation, leaking it through the TLB. It is exactly the kind of
ambiguous, high-stakes report where an automated, evidence-bound loop is useful.
We tested it three ways.

\textbf{Adaptation.} A reviewed adaptation of the mechanism was deterministic and
clean on the current pin (4 executions) and on the exact reported
Chipyard \texttt{004297b6}/BOOM \texttt{fac2c370} with historical
\texttt{SmallBoomConfig} (built in 685\,s).

\textbf{Original attachment.} We fetched the reporter's ELF by pinned URL and
digest, converted its entry-zero image to a fixed load image, and captured a
VCD waveform at a fixed seed. Table~\ref{tab:gadget} summarizes the gadget. A scanner joins events by ROB index,
physical register, load-queue slot, and branch mask, and requires one ordered
chain within the first speculation window. The trace shows the trained branch
(cycle 3769), a branch-masked protected-page TLB request (3807), requests to
\texttt{0x59f} (from 3809), a page fault, and misprediction resolution (3910).
At first sight this looks like the reported leak. However, the disassembly shows that
\texttt{0x59f} is the address of an independent third load
(\texttt{lb s1, 1439(a0)} with a zero base; $1439 = \texttt{0x59f}$), not a
secret-derived address. The dependent load at gadget offset +4 issues with its source operand
poisoned while the LSU reports a load miss, and BOOM's register-read gate
(\texttt{exu/core.scala}, lines 973--978) drops its issue-valid, so it never
presents a valid LSU request.

\textbf{Repairs correctly rejected.} Four hash-pinned candidate LSU patches,
outside the closed repair list, were each evaluated against the matched baseline
trace: v1 same-cycle fault gates; v2 blocking loads under unresolved branches; v3 suppressing fast wakeup and
excepting-entry writeback; v4 requiring a registered D-cache fire before
speculative wakeup. V1--v3 left the \texttt{0x59f} chain cycle-identical to
baseline, and v4's waveform was not recovered. Because the baseline never
demonstrated the dependent-load mechanism, \emph{no} repair can be credited, and
every comparison seal records \texttt{security\_fix\_validated: false}. A loop
that accepted ``the patch built and nothing leaked'' would have declared success
four times here. The practical takeaway for the BOOM project is that this report,
on the revision as filed, does not exhibit the described leak, and the exact
mechanism that suppresses the dependent load is identified.

\textbf{Real BOOM baseline and live run.} A reviewed payload configures PMP to
deny a 4\,KiB page, drops to user mode via \texttt{mret}, and requires a
load-access fault (cause~5); the same ELF passed on Spike and SmallBoomV3, and two
programs (architectural denial and a transient window) were clean and
deterministic on the pristine core. Because pristine BOOM exhibited no violation,
we added a clearly labelled positive control that touches a secret-selected cache
line before entering user mode; it produced probe sequences
\texttt{[1],[0],[1],[0]} before repair and all zeros after, over 16 executions on
the \emph{same} simulator binary. Driven live on this control, Gemini~2.5
Flash-Lite proposed a six-operation program, BOOM confirmed the leak,
minimization kept \texttt{enter\_user, load\_secret, probe}, the repair agent
chose the closed repair, the witness retested clean, and the attacker reached
exhaustion: 28 BOOM executions, 4 Vertex calls, zero inconclusive cases, and
\$0.0006038 of accounted cost.

\textbf{Held-out corpus and candidate patch.} Eight fixed programs vary training,
encoding, squash and fence placement, and noise, all retaining the protected load.
With two repetitions in both secret worlds, all 32 mutated executions were
deterministic violations and all 32 repaired executions were clean --- a test that
the \emph{validator and repair gate} generalize across program shape, not an RTL
fix. Separately, source review of BOOM's \texttt{lsu.scala} found that incoming
and retried D-cache requests are not gated by same-cycle
\texttt{ae\_ld}/\texttt{pf\_ld}/\texttt{ma\_ld}; a two-path gate patch built into a
distinct simulator and ran the secure matrix cleanly (8/8). Since the baseline was
already clean, this shows only that the patch builds and does not break the target
tests; the seal records \texttt{security\_fix\_validated: false}.

Three lessons generalize. First, \emph{a clean result is only evidence if the
same test fails on the vulnerable variant}; four of the defects are versions
of this. Second, minimizers and scanners are adversarial surfaces: they
optimize for the property check, not the threat model, and must re-encode the
threat model as constraints. Third, a negative result on real RTL (issue~\#715)
required more infrastructure than the positive control, and it is also the
more informative of the two.

\section{Cost and Efficiency}\label{sec:cost}
\sh{} was built and evaluated inside a single \$300 GCP free-trial allocation and
requested no additional funding at any point. All model usage is exactly accounted
by the sealed cost ledgers and totals well under \$0.05 across every sealed and
development call: the live BOOM discovery-and-repair loop cost \$0.0006, the ten
repeatability trials \$0.0054, the CHIA-node run \$0.0005, and the early
integration smoke tests \$0.0047. Cloud compute was a small number of
short-lived, auto-deleting workers, each rebuilt from pinned sources and deleted
after its evidence was hashed; billing is delayed, but their recorded runtimes put
total project spend on the order of \$10. For context, the hackathon's funding
proposals were asked to target \$100--\$1{,}500; \sh{} produced real-BOOM RTL
evidence, a live agentic loop, and the issue~\#715 resolution for roughly a tenth
of the low end. The dominant cost is CPU time for cycle-accurate Verilator builds,
not model inference, which is a useful data point for anyone budgeting agentic RTL
security work: the LLM is nearly free relative to the simulator.

\section{Design Boundaries, Limitations, and Future Work}\label{sec:limits}
We found no new BOOM vulnerability; every successful discovery and repair is on an
intentional harness mutation, the live BOOM loop ran once, and the search
comparison uses three small fixtures. Two of these limits are deliberate design
boundaries rather than accidents. First, the attacker is confined to a closed set
of reviewed operations that the trusted runner compiles into fixed templates, and
the repair agent selects only closed identifiers. This boundary is simultaneously
a soundness mechanism --- no unreviewed code decides a verdict --- and a safety
mechanism, since an untrusted model never executes arbitrary privileged code on
the core; it also bounds the search space to combinations of primitives the loop
has been given. Second, general-purpose LLM assistants apply constraints to
offensive-security tasks, which, together with a hackathon-scale time and compute
budget, bounded how far the autonomous attacker was pushed. The
architecture, however, is unchanged by scale: widening the reviewed primitive set
(more speculation shapes, more covert-channel constructions, a richer observation
channel) and adding compute is the direct path to exercising broader
transient-execution behaviour, and reproducing a \emph{published} vulnerability
class is the natural next milestone before anything novel. Crucially, that path
does not weaken the guarantee that matters: the differential oracle and the
recomputable seals, not the model, would still decide every verdict.

\section{Related Work}\label{sec:related}
\sh{} sits at the intersection of three lines of work. \emph{Agentic discovery
loops} such as AlphaEvolve~\cite{alphaevolve} and VibeServe~\cite{vibeserve} show
that an LLM in an outer search loop with an inner correctness or performance check
can improve algorithms and build bespoke systems; \sh{} applies the same
propose-then-check structure to microarchitectural security and runs inside
CHIA~\cite{chia}, which expresses such flows as directed cyclic graphs over
hardware tools. \emph{Red-team LLM agents} such as PentestGPT~\cite{pentestgpt}
and the agents evaluated by Cybench~\cite{cybench} autonomously find and exploit
software vulnerabilities; \sh{} is a blue-team counterpart at the RTL level, where
that same autonomy is dangerous unless a deterministic oracle gates every claim.
\emph{Hardware fuzzing} drives RTL toward coverage without a security oracle
(RFUZZ~\cite{rfuzz}); differential fuzzing adds one by comparing a design against
itself under different secrets, the strategy our validator follows, and
hardware--software contracts~\cite{contracts} formalise what speculation may
expose. \sh{}'s specific contribution is the fail-closed evidence discipline: an
untrusted model may steer the search, but no claim survives that a deterministic
oracle and a recomputable seal do not independently support.

\section{Conclusion}
\sh{} shows that an LLM-driven security loop on real out-of-order RTL is cheap to
run --- on the order of \$10 end-to-end, with the model nearly free --- and that
its credibility comes from a validator that fails closed. Its most practical
result is the automated resolution of open BOOM report~\#715. The loop, pinned
BOOM runners, and every sealed artifact are open source at
\url{https://github.com/Ryclic/SpecHunter}.
